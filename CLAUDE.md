# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Run

This is an ASP.NET Web Forms solution targeting .NET 4.7.2. Open `WebApplication12.sln` in Visual Studio and run with IIS Express (F5). The app is compiled inside Visual Studio (or with the VS 2022 MSBuild: `MSBuild.exe WebApplication12.sln /t:Build`); the NuGet packages must be restored first (right click the solution → Restore NuGet Packages).

The app starts at `Login.aspx` (configured as default document in `Web.config`).

## Database Setup

Run `DAL/BD_Universidad.sql` and then `DAL/Multiidioma_Actualizacion.sql` against SQL Server (`sqlcmd -S . -E -b -f 65001 -i <file>`) to create the database `BDUNIVERSIDAD`, all tables and all stored procedures. Both scripts are idempotent (safe to re-run on a database that already holds data). They insert NO business data: users, profiles, permissions and the plan de estudios (51 materias, 43 correlativas) are seeded by `SiembraBLL` the first time the application starts (see "Digit verifier" and "Data encryption"). The script does not migrate data: if it finds the old plaintext schema (`USUARIO.USUARIO` is not `varbinary`) it raises an error and stops (`SET NOEXEC ON`); drop the database and run it again.

**Delivery-machine setup:** (1) create the database with the two scripts, (2) copy `Web.config` with the same `AesKey`/`AesIV` (without them nothing in the database can be read), (3) adjust `Data Source` in `DAL/Acceso.cs` if the instance is named, (4) start the application once (open `Login.aspx`): it seeds profiles, users and the plan de estudios and computes the integrity digits.

The connection string is hardcoded in `DAL/Acceso.cs`:
```
initial catalog=BDUNIVERSIDAD; Data Source=.; Integrated Security=SSPI
```
Change `Data Source=.` if the SQL Server instance is named (e.g. `.\SQLEXPRESS`).

Default credentials (created by the application's first start on an empty database): `admin` / `Admin123`, `webmaster` / `Webmaster123`

## Architecture

Four-project layered solution: **BE → DAL → BLL → WebApplication12**.

- **BE** — Plain entity classes (`USUARIO`, `MATERIA`, `ALUMNO_MATERIA`, `PERIODO_ACADEMICO`, `INSCRIPCION`, etc.) plus `AESHelper` (deterministic AES-CBC for every business column, with typed helpers), `Normalizador` (search keys), `PoliticaBloqueo` (lock-out rule), `HashHelper` (SHA-256), and the permissions Composite (`NodoPermiso`, `Rol`, `Permiso`, `Permisos` constants).
- **DAL** — `Acceso.cs` is the central DB gateway (all queries go through `Abrir()` → stored proc → `Cerrar()` in finally). Every DAL class uses `Acceso` exclusively; no inline SQL anywhere. Methods: `Leer()` → DataTable, `Escribir()` → rows affected, `EscribirConRetorno()` → SCOPE_IDENTITY.
- **BLL** — Business logic + audit trail. Every write operation calls `BitacoraBLL.RegistrarAccion()`. Contains `AlumnoMateriaBLL` (includes DVH/DVV digit-verifier logic), `InscripcionBLL`, `PeriodoBLL`, `MateriaBLL`, `UsuarioBLL`, `LoginBLL`, `EventoBLL`.
- **WebApplication12** — ASP.NET Web Forms pages. All pages inherit `Site.Master`. Session authentication: every page checks `Session["Usuario"]` (cast to `BE.USUARIO`) on `Page_Load`.

## Role-Based Access (dynamic profiles, Composite)

Access is controlled by **permissions**, not by a fixed role string (`USUARIO.ROL` no longer exists).

- **Schema:** `ROL` (profile, `PADRE_ID` self-FK, `PROTEGIDO`), `PERMISO`, `ROL_PERMISO`, `USUARIO_PERFIL` (many-to-many user↔profile). Base profiles seeded by `SiembraBLL`: `Administrador` and `Webmaster` (protected), `Alumno`. The legacy `USUARIO.ROL` migration path (`MIGRACION_USUARIO_ROL`) was removed together with data migration.
- **Composite (real inheritance):** `BE.Rol` contains child `Rol`s and `Permiso` leaves. `TienePermiso` / `ObtenerPermisos` resolve recursively, so a parent profile also grants every permission of its descendants. `BLL.PerfilBLL` loads the whole tree once (in memory) and computes the user's effective permissions; `LoginBLL` stores them in `BE.USUARIO.Permisos` (kept in `Session["Usuario"]`). Never resolve effective permissions with a flat SQL query. `PerfilBLL.CambiarPadre` rejects cycles.
- **Permission names** are centralized in `BE.Permisos` (ASCII, no accents — they are matched as text against `PERMISO.NOMBRE`).
- **Web gating:** pages inherit `PaginaBase` and declare `PermisoRequerido` (or override `TieneAcceso`). Missing session → `Login.aspx`; missing permission → the user's home page (`PaginaBase.ObtenerPaginaInicio`, picked by permission priority).
- **Navigation:** `Site.Master.cs` shows each sidebar link only if the user has its permission; one `asp:PlaceHolder` per link and per section.
- **Profile management:** `Perfiles.aspx` (tree of profiles/permissions; create, rename, move, delete, set direct permissions, read-only effective permissions) and `AsignarPerfiles.aspx` (user ↔ profiles), both gated by `Gestionar perfiles`. All rules live in `PerfilBLL`: protected profiles are read-only (no rename/move/delete/permission edits); a profile with children or assigned users cannot be deleted; cycles are rejected; no change may leave the system without a user whose effective permissions include `Gestionar perfiles` (changes are simulated in memory first). Every write recalculates DVH/DVV of the touched tables and goes through `BitacoraBLL`.
- **User management:** `Usuarios.aspx` (permission `Gestionar usuarios`, granted to Administrador by `SiembraBLL`): create user + profiles in one transaction (`UsuarioDAL.InsertarConPerfiles`), edit address/profiles, reset password, and logical deactivation via `USUARIO.ACTIVO` (no physical delete: FKs to cursadas and bitácora). Login rejects inactive users; an inactive or blocked user does not count as an operator in the last-operator guard; nobody can deactivate themselves. Rules live in `PerfilBLL` (same write lock and `PostEscritura` pattern). **Escalation rule** (enforced in the BLL, pages only mirror it via `ListarRolesAsignablesPor` / `ListarUsuariosActuablesPor`): an actor "covers" a set of permissions if, without `Gestionar perfiles`, he owns all of them (subset rule); with `Gestionar perfiles` he only needs to own the *privileged* ones (`BE.Permisos.Privilegiados`: Gestionar perfiles/usuarios, Verificar integridad, Ingresar con integridad invalida, Desbloquear usuarios), so Administrador still manages alumnos but can never touch Webmaster users, assign the Webmaster profile or grant its permissions. The actor must cover the effective permissions of the target user (edit, reset password, deactivate, assign profiles), of every profile assigned or removed, and, for profile writes (`GuardarPermisosDeRol`, `CambiarPadre`, `EliminarRol`), both the profile's current effective permissions and the permissions being granted. There is no special case for protected profiles. Visibility follows the same rule: management listings (`ListarUsuariosVisiblesPor` for `Usuarios.aspx`/`AsignarPerfiles.aspx`, `ListarBloqueadosVisiblesPor` for `UsuariosBloqueados.aspx`) only return users the actor can act on, and any BLL operation or read given an id/name the actor cannot see fails with the same "El usuario no existe." as a nonexistent one (`DesbloquearUsuario` also requires `Desbloquear usuarios`). Profiles follow the same rule: a profile is visible only if the actor covers its effective permissions (the assignable set; for `Perfiles.aspx` writes the profile must also be *manageable*, i.e. it and every ancestor are visible, since a change alters the effective permissions of the whole ancestor chain: `ListarRolesGestionablesPor` / `ObtenerArbolGestionablePor` / `ObtenerRolGestionablePor`. Visibility is monotone downwards — a visible profile has a fully visible subtree — so the manageable tree is the set of full subtrees of visible root profiles; a profile hanging from a hidden one is not shown at all). Read methods also check the capability permission (`Gestionar usuarios` or `Gestionar perfiles` for user reads, `Gestionar usuarios` for addresses, `Gestionar perfiles` for profile reads); `Perfiles.aspx` only lists permissions from `ListarPermisosOtorgablesPor`, and a hidden profile or non-grantable permission is rejected with the same message as a nonexistent one. Known leaks left on purpose: editing a visible profile that is shared with a hidden user also changes that user's permissions, duplicate profile names ("Ya existe un perfil con ese nombre."), the "profile has users assigned" delete guard, the unique-username check on create, `Bitacora.aspx` (audit log) and `Notas.aspx` (grading list of users with `Inscribirse a materias`). The seeded Webmaster profile also has `Gestionar usuarios` and `Desbloquear usuarios` so it can manage and unblock webmaster accounts (Administrador cannot); on an already-seeded database that grant is not added automatically (the seed only grants newly created catalog permissions), so recreate the database or insert the `ROL_PERMISO` row and recalculate its integrity. Backups carry a `Version` field (`IntegridadBLL.VersionBackup`, currently 3) and a `ClaveControl` canary (Base64 of the AES encryption of `IntegridadBLL.TextoControlClave`); `RestaurarDesdeBackupJson` rejects any other version (old plaintext backups included), a missing canary or one made with another `AesKey`/`AesIV`, and validates every cell of every table (Base64, AES block length, column size from `EspecColumnas`, integer ids/FKs, repeated ids/unique values) before saving any snapshot, so a bad backup changes nothing. All snapshot/backup JSON goes through `IntegridadBLL.CrearSerializador` (`MaxJsonLength = int.MaxValue`).
- **Session refresh:** `PerfilBLL.VersionPermisos` is a static counter bumped on every profile write; `USUARIO.VersionPermisos` stores the version the session loaded, and `PaginaBase`/`Site.Master` recalculate `Permisos` when it is stale (InProc sessions only).
- **Not a permission:** "Alumno" as a domain identity (has cursadas) means having the `Inscribirse a materias` permission (effective, so child profiles count); see `UsuarioBLL.ListarAlumnos` (grading list). Login blocks users when integrity fails unless they have `Ingresar con integridad invalida`, which only the seeded Webmaster profile has (Administrador is blocked like alumnos).

**Important:** The sidebar uses `asp:PlaceHolder` (not Panel) to wrap `<li>` elements — Panel renders a `<div>` which is invalid inside `<ul>`.

## Key Patterns

**DAL pattern:**
```csharp
try { _acceso.Abrir(); /* query */ }
finally { _acceso.Cerrar(); }
```

**Stored procedures only** — all DB access via named stored procs. Proc names follow the pattern `ENTIDAD_ACCION` (e.g. `MATERIA_LISTAR`, `ALUMNO_MATERIA_ACTUALIZAR`).

**Inscripción flow:** `InscripcionBLL.Inscribir()` checks correlativas before inserting. If a cabecera already exists for the period it reuses it (via `INSCRIPCION_OBTENER_ID`) instead of blocking re-enrollment — students can add more subjects to an existing enrollment.

**Data encryption:** see the dedicated section below. **Digit verifier:** all 13 business tables (the original 9 plus `ROL`, `PERMISO`, `ROL_PERMISO`, `USUARIO_PERFIL`) have a `DVH` column computed per row by `BE.CalculadorDVH`. Column lists (`Columnas*`) live in `BLL/IntegridadBLL.cs`; the vertical digits (DVV) are stored per table+column in `DIGITO_VERIFICADOR_VERTICAL`. `IntegridadBLL` verifies/recalculates every table, exports/restores a JSON backup, and `Integridad.aspx` (permission `Verificar integridad`) drives it. `ROL_PERMISO` and `USUARIO_PERFIL` carry an `ID IDENTITY` column (like `CORRELATIVA`) because the engine works with one integer ID per row. At startup `Global.asax.cs` calls `IntegridadBLL.IntentarInicializarDatosBase()` (retried first thing in `LoginBLL.AutenticarUsuario` if it failed): `SiembraBLL` seeds the base permissions/profiles/users once (marker = bitácora entry `SIEMBRA_DATOS_BASE`, written in the same transaction; users are created only on an empty `USUARIO` + `ROL`, profiles only on an empty `ROL`, the plan de estudios (`SiembraBLL.MateriasDelPlan()` / `CorrelativasDelPlan()`) only on an empty `MATERIA` without marker; otherwise it only adds missing catalog permissions and never recreates profiles, users or materias) and `InicializarTablasNuncaCalculadas` computes the integrity of tables with no DVV/snapshot only on a virgin install (no marker and no users: all 13 tables) or on a pre-profiles database without marker (USUARIO + the 4 profile tables, as before). On a database in use a table without DVV is reported invalid and is NOT self-healed (it would accept tampering); the tables the seed itself invalidated are recalculated by `SiembraBLL` (in-memory pending set, retried on the next login; after a restart use the recalculate action in `Integridad.aspx`). Known window (fail-closed by design): on a virgin install, if the process restarts after the seed commits but before `InicializarTablasNuncaCalculadas` finishes, the marker already exists, so the remaining no-DVV tables (e.g. `MATERIA`, `CORRELATIVA`) are reported invalid until the Webmaster recalculates them from `Integridad.aspx`.

**Pagination:** the reusable pager is the user control `Paginador.ascx` (registered per page with `<%@ Register Src="~/Paginador.ascx" TagPrefix="uc" TagName="Paginador" %>`) plus the DTO `BE.PaginaResultado<T>` (Filas, TotalFilas, Pagina, Tamanio, TotalPaginas). A page queries with `paginador.PaginaActual` / `TamanioPagina`, binds `resultado.Filas`, calls `paginador.Establecer(resultado)` and re-binds on the `CambioPagina` event. `BLL.Paginacion.ConsultarAjustando` re-queries the real last page when the requested one is past the end (rows deleted, filter changed), so a grid is never shown empty by mistake. `Materias.aspx` (10 per page) pages server-side (`MATERIA_LISTAR_PAGINADO`: `OFFSET/FETCH` + `COUNT(*) OVER() AS TOTAL_FILAS`); `Bitacora.aspx` (50 per page) filters user and criticidad in SQL by encrypted equality (`BITACORA_LISTAR_FILTRADO`, ordered by `ID DESC` as proxy for `FECHA DESC`) and applies the date range and the paging in C# (`BitacoraDAL.Paginar`), because dates are ciphertext. `Usuarios.aspx` (10 per page) pages **in memory, after** the visibility filter (`PerfilBLL.ListarUsuariosVisiblesPor(actor, pagina, tamanio)`): the rule lives in the Composite in C#, and paging in SQL first would give short pages and a total that reveals hidden users. Row commands use `CommandArgument = Id`, never the row index, so they work on any page. Bounded grids (Inscripcion, MisCursadas, Notas, Calendario, etc.) intentionally do not page.

**Card-based materia selection:** Checkboxes in `Inscripcion.aspx` use `name="materiaId"` inside `<label>` wrappers; server reads them via `Request.Form.GetValues("materiaId")` (not from a CheckBoxList).

**Multi-language (Observer + Facade, same design as `ingenieria_software`):** tables `IDIOMA`, `CONTROL_IDIOMA` (key + default Spanish text) and `TRADUCCION` (text per language); `USUARIO.IDIOMA_ID` stores the user's preference and is deliberately NOT in `ColumnasUsuario` (changing language is not a data tamper). These tables have no DVH. `BE.IdiomaManager` is the Subject (observers + active language + dictionary) and `BE.IObservadorIdioma` the Observer; unlike the WinForms Singleton there is **one manager per session** (`CAPAS_Web.IdiomaWeb.Manager`), because a static one would mix users. `BLL.FachadaIdioma(manager)` is the Facade; `IdiomaBLL` has the rules (default language cannot be deleted/disabled, nor one in use) and `IdiomaBLL.VersionTraducciones` is a static counter bumped on every edit so sessions reload their dictionary (same idea as `PerfilBLL.VersionPermisos`, InProc only). `PaginaConIdioma` is the ConcreteObserver (the `FormBase` equivalent) and `PaginaBase` and `Login` inherit it: on init it records the original text of every `asp:Literal` and `asp:Button` that has an **ID** (key = `Page.ControlId`, the class that declared it: page, `Site` master or user control) and on every pre-render it puts the translated text back. Static markup text must therefore be written `<asp:Literal ID="litX" runat="server" Text="..."/>` (never a `Label`, which holds runtime values; Literals are forced to `Encode` mode). Text built in code uses `Textos.T(key, default, args)`, and `Textos.TH(...)` (HTML-encoded) whenever it is assigned to a `Label.Text` or `LinkButton.Text`, which do not encode. Keys register themselves in `CONTROL_IDIOMA` on first use. `SelectorIdioma.ascx` (master + Login) changes the language through the Facade; `Idiomas.aspx` (permission `Gestionar idiomas`, granted to Administrador and Webmaster) manages languages and translations. English and Portuguese texts come from `DAL/traducciones.sql` (idempotent, run it after `BD_Universidad.sql`; it never deletes keys). Translated so far: master, Login, Materias, Dashboard, Paginador and Idiomas; to translate another page, replace its static texts with named Literals, use `Textos.T` for code strings and add the keys to `traducciones.sql`.

## Data encryption (application-level AES)

If someone opens the database in SSMS, no business data is readable. Every data column of `USUARIO`, `BITACORA`, `MATERIA`, `ALUMNO_MATERIA`, `EVENTO_ACADEMICO`, `PERIODO_ACADEMICO`, `INSCRIPCION`, `ROL` and `PERMISO` is `varbinary` (text, numbers, grades, dates and bit flags). Only primary keys, foreign keys (including `USUARIO.IDIOMA_ID`, `ROL.PADRE_ID`), `DVH`, `DIGITO_VERIFICADOR_VERTICAL` and the language tables stay in clear.

- **Cipher:** `BE.AESHelper` (AES-CBC, key and IV from `appSettings` `AesKey`/`AesIV` in `Web.config` and `UnitTests/app.config`). The IV is fixed, so it is **deterministic**: equal plaintext gives equal ciphertext, which is what makes `WHERE USUARIO = @usuario` / `UNIQUE` constraints / equality filters work with an encrypted parameter. Typed helpers (`EncriptarEntero/Bool/Decimal/Fecha`, `DesencriptarTexto/Entero/Bool/Decimal/Fecha`) use one canonical, culture-independent format (invariant integer, `F2` decimal, `yyyy-MM-ddTHH:mm:ss.fff` date, `1`/`0` bool). Reads are tolerant: tampered ciphertext decrypts to `AESHelper.TextoIlegible` / `0` / `null` instead of throwing, so the Webmaster can still reach `Integridad.aspx`.
- **Where it happens:** the DAL encrypts parameters and decrypts results (`Acceso` only moves `byte[]`); entities and the BLL work with plaintext. Stored procedures only store, compare ciphertext for equality and return it. Anything SQL cannot do on ciphertext is done in C#: ordering by a data column (`ORDER BY` only on `ID`; the DAL sorts after decrypting), `YEAR/MONTH` of events, "current period", the period label, the date range and paging of the bitácora, and the login attempt counter (`UsuarioDAL.IncrementarIntentos`: read with `UPDLOCK` + write inside one transaction, rule in `BE.PoliticaBloqueo`, max 3). Every value that used to come from a SQL `DEFAULT` (`GETDATE()`, `ACTIVO`, `PESO`, `ESTADO`, `CRITICIDAD`...) is now supplied by C#.
- **Normalization before encrypting** (varbinary lost the case-insensitive collation): `USUARIO.USUARIO` -> `BE.Normalizador.Usuario` (trim + lower), `MATERIA.CODIGO` -> `BE.Normalizador.CodigoMateria` (trim + upper). Applied on login, create, lookup, duplicate checks, XML import and seeding. Never compare or search these fields without normalizing first. Profile/permission names are not normalized (the BLL duplicate check is case-insensitive).
- **Passwords:** the SHA-256 hex hash is wrapped in AES (`PASS` stores `AES(SHA256(password))`) and login compares the encrypted hash by equality.
- **Integrity over ciphertext:** `IntegridadBLL.Extraer*` takes the Base64 of each varbinary (`Base64Str`), so DVH, DVV and `SNAPSHOT_INTEGRIDAD.DATOS_JSON` hold only ciphertext (plus clear ids) and verifying integrity never needs the key. Only the diagnostic messages (`DiagnosticarDiferencias` -> `ValorLegible`, per-table `ColumnasCifradas` map) decrypt, for readability; `PASS` is never shown. Restore passes the ciphertext bytes straight through (`*_RESTAURAR_FILA` take `varbinary`). If you add or encrypt a column, update `Columnas*`, `ColumnasCifradas`, the `Extraer*`/`Rehidratar*` pair, the restore proc and `IntegridadDAL.RestaurarFila*` together (`IntegridadCifradaTests.TodasLasTablas_...` checks the extractors against those maps).
- **Adding a new business table or column:** make it `varbinary` (size generously: ~16 bytes of overhead plus 16-byte blocks), encrypt/decrypt in its DAL, never write inline SQL against it, and add it to the integrity engine and to `CifradoEnBaseTests` expectations.
- **Input length:** an over-long value would fail with "String or binary data would be truncated" on the varbinary column, so `BLL.ValidacionLongitud` (materia name/code/modalidad, event and period description) and `PerfilBLL.ValidarDireccion`/profile name/username check the plaintext length first (max chars chosen so the 3-byte UTF-8 worst case still fits the column) and the TextBoxes carry a matching `MaxLength`. If you change a column size, update those limits, `EspecColumnas` and the tests.
- **Do not** put business data in clear anywhere else (logs, snapshots, bitácora text built with names is fine because the bitácora itself is encrypted).

## Tests

`UnitTests/` is an MSTest project (SDK-style, `net472`, referenced from the solution). Run it from Visual Studio (Test → Test Explorer) or, after building the solution, with `dotnet test UnitTests\UnitTests.csproj --no-build` (add `--filter "TestCategory!=Integracion"` to skip the database tests).

- **Unit tests (no database):** `BE` (digit verifier, SHA-256, AES and typed encryption, lock-out policy, Composite of profiles/permissions, `SessionRegistry`, `IdiomaManager` Observer), `BLL` (XML import validation and prerequisite cycles, academic risk, calendar heat map, `Paginacion`, bitácora paging, integrity extractors over ciphertext, versioned backup validation, plan de estudios, permission catalog), `Web` (`Textos` keys and message templates) and `Consistencia` (SQL scripts have no BOM, the combined script contains the separate ones, and every translatable text in the code and markup has its row in `DAL/traducciones.sql`).
- **Integration tests (`[TestCategory("Integracion")]`):** checks against the real database using the connection string compiled in `DAL/Acceso.cs` (languages and translations, materias, seeded profiles, integrity, and `CifradoEnBaseTests`: every business column is `varbinary`, no readable text in the tables, snapshots and backup). They are read-only except `ElBackup_ExportarYRestaurar_...` (`TestCategory("Escritura")`, restores the current state onto itself). Without a database they are reported as skipped, not failed; run the SQL scripts and start the app once to seed it (the materias only exist after the application seeds them).
- Private logic (`BuscarCiclo`, `CalcularRiesgo`, `Textos.Plantillas`) is reached by reflection so production code is not changed for the tests; if you rename those members the tests say so.
- When you add a translatable text (a `Literal`/`Button`/`LinkButton` with an ID, or a `Textos.*` call) add its row to `DAL/traducciones.sql` and `DAL/Multiidioma_Actualizacion.sql`; `CadaTextoTraducibleDelCodigo_TieneFilaEnElScript` and `LosLiteralesYBotonesConIdDelMarkup_TienenFilaEnElScript` fail until you do.
